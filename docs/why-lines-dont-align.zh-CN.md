# 线为什么还是对不齐

*一份测量记录。这里的每个数都是 2026-09-08 在生产环境上量的，不是估的。这一版没有重测那个站点。*

Dr Non 的问题：**「有时我说了 MoMA 规则，系统仍然允许对不齐的线。为什么？」**

有五个答案。只有第一个关乎纪律。另外四个是机械的。所以把那几个字说出来，从来不够。

---

## 1. 规则是散文，散文不执行

MoMA 规则住在 `docs/lessons/2026-08-20-the-moma-pass.md`——一则课，描述六处改动，改过一次，改在一页上。

2026-09-08 核对过：

- `grep -ci moma CLAUDE.md` → **0**。每个代理都会读的那份文件里没有这些规则。
- 两个仓库里没有测试、没有 lint 规则、没有 CI 作业提到对齐。
- 那则课自己的收尾说，审计 **只做了首页**，并列出 `/trade`、`/signals`、`/portfolio`、`/simulate`、`/plan` 为从未审计。

一条没有东西执行的规则，会被每一个新组件重新争论。而每一个新组件，是由一个没读过那则课的人（或东西）写的。第一次修补是真的。它只是没有办法传开。

---

## 2. 没有一套间距，所以对齐在算术上不可能

两个元素落在同一条边上，是因为它们的间距来自同一套小数目。在 `src/` 上量过：

| | daytraders | day2 |
|---|---|---|
| 不同的间距值 | **86** | 25 |
| 使用次数 | 5,028 | 402 |
| 不在任何 4px 网格上 | **40.1%** | 37.1% |
| 定义了的间距记号 | **1**（`--gap: 12px`） | 0 |

出格的值包括 1、3、5、7、9、11、13、15、18、22、26、34、35、37、38、42、45、50、58、70、95、97、110、118、222px。

你无法对齐 86 个值。不是更小心就能对齐，也不是多审一遍就能对齐。套子必须先关上。那是第二条法，也是其他每一条法的前提。

---

## 3. 页面的主原点自己就不在刻度上

```css
--cockpit-x: 22px;   /* 每个平面继承的水平原点 */
```

22 不是 4 的倍数。它上面在 `globals.css` 里的注释说得对：每个平面都读这个值，「所以边靠构造就重合」——它们确实重合，重合在一个系统里其他间距都够不着的值上。这个已知数是健全的。它的值不在刻度上。

---

## 4. 发丝线把它框住的一切都挪了

这是机械的心脏，而且在代码审查里看不见。

在 1280×900 上现场量的：

| 容器 | 它怎么定原点 | 盒子的左 | 第一个子元素的左 |
|---|---|---|---|
| `.rams-masthead` | `padding-left: 22px`，无边框 | 0 | **22** |
| `.rams-cell-grid` | `border: 1px`，`padding-left: 0` | 22 | **23** |
| `.picks-grid` | `border: 1px`，`padding-left: 0` | 22 | **23** |

两个容器要的是同一个原点。孤立地看，两个都「对」。可是边框参加布局，同样数值的内边距不参加。所以带框网格里的每一个格子，都正好坐在它上面那个字标内侧 1px 的地方。

测量时：**124 个元素在 x=22，62 个元素在 x=23。**

造成它的那个模式是个好模式——发丝线网格：`gap: 1px` 铺在 `background: var(--line)` 上，不用额外标记就画出每一条内线：

```css
.rams-cell-grid {
  display: grid;
  gap: 1px;
  background: var(--line);
  border: 1px solid var(--line);   /* 这一行把每个子元素推开 */
}
```

修补是一个属性：用阴影做框。阴影画出来，不占空间。

```css
  box-shadow: inset 0 0 0 1px var(--line);
```

现场用上之后，网格子元素的偏移从 **1px 变成 0**，并把十个元素拉上共享的原点（x=22：124 → 134）。

---

## 5. ……而且就地修好，让整页更糟

这是最要紧的发现，也是前几次 MoMA 清扫一直退回去的原因。

同一处修补现场用上之后，全页的近失数量 **上升** 了：

```
修补前：856 对近失的边
修补后：905 对近失的边    （+49）
```

容器这一层的修补是对的，而且做到了它声称的事。可是把一族元素拉上原点，它们的后代也跟着挪了 1px。那些后代于是落在离 *另一族* 1px 的地方，而那一族本来也不在原点上。1px 的漂移不是两个组件里的缺陷。它是一页有 86 个间距、31 种列节奏时的环境状态。

**对齐不能一个元素一个元素地修。** 每一次局部改正都把误差重新分配。它只能靠把值的集合关上——一个原点，十五个间距，四种密度（192、296、400、608）——然后用每次提交都跑的检查把它们关住。

这就是这个仓库。

---

## 什么真的守得住

| 失败 | 法 | 由谁执行 |
|---|---|---|
| 规则住在散文里 | — | CI 里的 `lint/`，以及只减不增的基线 |
| 间距的套子是开的 | 二 | `spacing-scale` |
| 原点不在刻度上 | 一 | 记号上的 `spacing-scale` |
| 发丝线推开子元素 | 一 | `origin-mechanism`，在 LAWS.md 里被命名，没有实现 |
| 31 种列节奏 | 五 | `grid-density` |
| 空格 | 四 | `orphan-grid`（运行时） |
| 一行高低不齐 | 六 | `ragged-row`（运行时） |
| 1–6px 的漂移 | 七 | `near-miss`（运行时） |

静态的那一半可以在源码上跑。CI 把它跑在 `examples/` 上，然后跑 `lint/self-check.mjs` 和 `lint/laws-check.mjs`。运行时的那一半，要等有人把 `audit/near-miss.browser.js` 贴进控制台才跑。近失、空格、一行高低不齐，都要等浏览器排完版才存在——所以读代码从来抓不住它们。为「发丝线推开子元素」命名的那个检查 `origin-mechanism`，仍然没有实现。

## 方法

- 静态：`node lint/moma-lint.mjs <目录> --strict`
- 运行时：在固定视口的页面里执行 `audit/near-miss.browser.js`
- 现场测量取自 `https://day.nonarkara.org`，1280×900，2026-09-08，1,793 个已布局的元素
